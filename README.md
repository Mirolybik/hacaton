# Hackathon — система управления заявками ветропарка

## 1. О проекте

Веб-приложение для учёта оборудования и управления заявками на техническое обслуживание ветропарка.

Система предназначена для регистрации заявок на осмотр и ремонт оборудования, назначения исполнителей и контроля выполнения работ.

## 2. Используемые технологии

**Frontend (клиентская часть):**
- React — создание пользовательского интерфейса.
- TypeScript — разработка с проверкой типов.
- Vite — сборка и запуск фронтенда.
- Nginx — веб-сервер для размещения приложения.

**Backend (серверная часть):**
- Node.js — среда выполнения JavaScript.
- Express — обработка HTTP-запросов.
- TypeScript — разработка серверной логики.
- Sequelize — взаимодействие с базой данных.

**База данных:**
- PostgreSQL — хранение информации об оборудовании и заявках.

**Дополнительные инструменты:**
- Docker и Docker Compose — запуск приложения в контейнерах.
- Git и GitHub — контроль версий и совместная разработка.
- Postman — проверка API.
- Node.js Test Runner — автоматическое тестирование API.

## 3. Архитектура приложения

Приложение состоит из трёх основных сервисов.

**Frontend**

Отображает страницы, формы, списки оборудования и заявок. Отправляет запросы серверу.

**Backend**

Принимает запросы от фронтенда, выполняет бизнес-логику, проверяет права доступа и взаимодействует с базой данных.

**Database**

Хранит информацию, необходимую для работы приложения.

Схема взаимодействия:

```text
Пользователь
    |
    v
React + Nginx
    |
    v
Node.js + Express
    |
    v
PostgreSQL
```

## 4. Установка и запуск

Для запуска необходимо установить:

- Git.
- Docker Desktop с поддержкой Docker Compose.

### Шаг 1. Клонирование репозитория

```bash
git clone https://github.com/Mirolybik/hacaton.git
cd hacaton
```

### Шаг 2. Запуск приложения

```bash
docker compose up -d --build
```

Эта команда собирает необходимые Docker-образы и запускает контейнеры.

### Шаг 3. Проверка контейнеров

```bash
docker compose ps
```

### Шаг 4. Открытие приложения

Frontend:

http://localhost:8080

Backend:

http://localhost:3000

Проверка состояния API:

http://localhost:3000/api/health

### Шаг 5. Остановка приложения

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume. Чтобы не потерять базу данных, не используйте параметр `-v` при остановке контейнеров.

## 5. Функциональность приложения

Система предназначена для следующих задач:

- Учёт оборудования ветропарка.
- Создание заявок на техническое обслуживание.
- Регистрация заявок на ремонт.
- Назначение инженеров для выполнения работ.
- Отслеживание текущего состояния заявок.
- Завершение работ с указанием комментария.

Доступность конкретных функций зависит от версии приложения и интегрированных модулей.

## 6. Типы заявок

Предусмотрены два основных типа заявок.

**Inspection (осмотр)**

Используется для плановой проверки и технического осмотра оборудования.

**Repair (ремонт)**

Используется при обнаружении неисправности или необходимости ремонта оборудования.

## 7. Статусы заявок

**new — Новая**

Заявка создана и ожидает принятия в работу.

**in_progress — В работе**

Инженер принял заявку и приступил к выполнению работ.

**waiting_parts — Ожидание запчастей**

Выполнение работ приостановлено до получения необходимых материалов или деталей.

**done — Выполнена**

Работы завершены, заявка закрыта.

## 8. Роли пользователей

В модуле заявок предусмотрены следующие роли.

**Дежурный (duty)**

Создаёт заявки на осмотр или ремонт оборудования.

**Инженер (engineer)**

Принимает заявки в работу и выполняет необходимые действия для их завершения.

**Руководитель (director)**

Роль для управленческих сценариев работы с системой.

Конкретные разрешения определяются серверной реализацией.

## 9. API

API обеспечивает взаимодействие клиентской и серверной частей приложения.

### Проверка доступности сервера

```http
GET /api/health
```

### Создание заявки

```http
POST /api/requests
```

### Получение заявки

```http
GET /api/requests/:id
```

### Принятие заявки в работу

```http
POST /api/requests/:id/take
```

### Изменение заявки

```http
PATCH /api/requests/:id
```

Указанные маршруты заявок использовались при тестировании отдельной QA-версии проекта. Перед использованием необходимо убедиться, что соответствующий модуль подключён в запускаемой версии сервера.

## 10. Тестирование

Для проверки работоспособности приложения используются ручные и автоматические тесты.

### 10.1. Тестирование через Postman

Postman используется для отправки HTTP-запросов к API и проверки ответов сервера.

Файл коллекции:

```text
tests/postman/Hackathon API Tests.postman_collection.json
```

Коллекция включает проверки:

- Доступности API.
- Обработки несуществующих маршрутов.
- Обработки неподдерживаемого HTTP-метода.
- Создания заявки.
- Принятия заявки инженером.
- Закрытия заявки.
- Получения информации о заявке.

Перед запуском необходимо настроить адрес тестируемого сервера в переменной `baseUrl`.

### 10.2. Автоматические тесты

Для автоматического тестирования используется встроенный Node.js Test Runner.

Файл тестов:

```text
tests/api/requests.test.cjs
```

Запуск тестов:

```bash
npm test
```

Реализованы шесть автоматических тестов:

1. Проверка работоспособности API.
2. Проверка полного жизненного цикла заявки.
3. Проверка запрета принятия заявки дежурным.
4. Проверка запрета создания заявки инженером.
5. Проверка создания заявки с несуществующим оборудованием.
6. Проверка запрета закрытия новой заявки без принятия в работу.

Дополнительно в тесте жизненного цикла проверяется запрет повторного закрытия завершённой заявки.

Последний подтверждённый результат в отдельном QA-окружении:

- Всего тестов: 6.
- Успешно: 6.
- Ошибок: 0.

### 10.3. Тестовое окружение

Для проверки API заявок использовалась отдельная тестовая среда.

```text
API: http://localhost:3001
PostgreSQL: localhost:55432
Database: hacaton_qa
Test equipment: QA-TEST-001
```

Для прохождения тестов необходим работающий API с реализованными маршрутами заявок и подготовленная база данных.

Не рекомендуется запускать автоматические тесты, создающие и изменяющие заявки, на рабочей базе данных.

## 11. Работа с Git и GitHub

Проект разрабатывается совместно с использованием системы контроля версий Git.

Для каждой новой задачи рекомендуется создавать отдельную ветку.

Пример создания ветки:

```bash
git switch -c feature/new-functionality
```

Добавление изменений:

```bash
git add .
```

Создание коммита:

```bash
git commit -m "feat: add new functionality"
```

Отправка ветки на GitHub:

```bash
git push -u origin feature/new-functionality
```

После отправки изменений создаётся Pull Request для проверки и объединения кода.
